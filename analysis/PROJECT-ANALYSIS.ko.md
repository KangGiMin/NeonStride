## 1. 전체 판단

NeonStride는 한국어 UI를 제공하는 SF 배경의 브라우저 무한 러너 게임이다. 프레임워크나 외부 JavaScript 패키지 없이 ES Modules, Canvas 2D, Web Audio, localStorage로 구성된다. 실제 3D 엔진을 쓰는 대신 자체 원근 투영과 절차적 도형으로 도시와 캐릭터를 그린다.

핵심 엔진과 캐릭터 애니메이션은 비교적 탄탄하다. 기존 테스트 40개가 모두 통과하고, 추가로 100개 난수 시드 × 4개 난이도 × 10분을 시뮬레이션한 400회 실행에서도 자동 조작이 모두 생존했다. 다만 이는 정답을 아는 자동 조작의 통과 가능성을 보여주며, 사람이 느끼는 난이도나 모든 가능한 난수열의 공정성을 보장하지 않는다.

현재 우선순위는 기능 확장보다 서버 오류 처리, 작은 화면과 가로 화면의 플레이 가능성, 키보드 이벤트 충돌, 테스트 독립성이다. 게임 자체의 실행 기반을 다른 프레임워크로 옮겨야 할 근거는 발견하지 못했다.

## 4. 실행 흐름과 아키텍처

```text
브라우저 → index.html → app.js
                          ├─ Runner: engine.js
                          └─ Scene: renderer.js → engine.js의 규칙 참조

키보드·포인터 → app.js → Runner 상태 변경
requestAnimationFrame → Runner.update(dt) → HUD 갱신 → Scene.render()
게임 종료 → 결과 표시 → 난이도별 localStorage 기록 갱신
```

역할 분리가 명확하다. 엔진은 DOM이나 Canvas 없이 실행할 수 있고 난수 함수를 주입받는다. 렌더러는 게임 상태를 읽어 그림을 만들며 자체적인 포즈 보간 상태를 보관한다. 앱 계층이 브라우저 입력·소리·저장소를 연결한다. 이 구조 덕분에 물리 엔진을 빠르고 재현 가능하게 시험할 수 있다.

반면 `app.js`에는 DOM 접근, 오디오, 저장, 상태 표시, 입력 정책이 한 파일에 모여 있고 UI 테스트도 모듈 전체를 한 번 가져오는 방식이다. 앞으로 기능이 늘면 입력 처리와 기록 저장부터 작은 모듈로 분리하는 편이 효과적이다. 지금 규모에서 복잡한 상태 관리 라이브러리를 추가할 필요는 낮다.

## 5. 게임 규칙과 상태

## 7. 그래픽과 애니메이션

장면은 Canvas 2D 위에 직접 그린다. 투영식은 대략 `k = 0.94 × 화면높이 / max(0.3, z + 7)`이며, x와 y를 이 비율로 축소해 원근감을 만든다. 별·일식·스카이라인·창문·간판·도로·난간·장애물·캐릭터를 모두 코드로 생성하므로 모델·텍스처·이미지 다운로드가 필요 없다.

캐릭터는 특히 공들인 부분이다. 6개 키를 이용한 3차 Hermite 보간으로 발의 위치와 속도를 연결하고, 허벅지 0.49 / 종아리 0.46 길이를 유지하는 역기구학 계산으로 무릎을 배치한다. 팔 길이는 0.30 / 0.28이다. 지지 발의 밑창 높이, 발끝으로 밀고 나가는 회전, 좌우 위상 차이, 팔의 반대 방향 스윙, 골반·몸통의 작은 회전이 구현돼 있다.

달리기 위상은 `distance × 0.045 + time × 10.8`이라 속도가 높아질수록 보폭 주기가 완만하게 증가한다. 점프 포즈는 지수 보간으로 섞고, 낙하 시에는 팔을 벌리고 몸이 기울어지는 별도 포즈를 쓴다. 떨어질 때 도로의 가까운 가장자리로 캐릭터를 가려 깊이를 표현한다.

실제 3D 깊이 버퍼 대신 장애물의 거리 정렬과 그리기 순서를 사용한다. 현재 단일 도로·단일 캐릭터에는 적합하지만 다수 캐릭터, 복잡한 지형, 서로 얽힌 물체를 추가하면 가림 순서를 재설계할 수 있다. 확장 시 고려할 제약이며 현 상태의 오류로 확인한 것은 아니다.

근거: [보행 키와 IK](../NeonStride/neon-stride/dist/renderer.js#L9), [투영](../NeonStride/neon-stride/dist/renderer.js#L225), [캐릭터](../NeonStride/neon-stride/dist/renderer.js#L992), [장면 순서](../NeonStride/neon-stride/dist/renderer.js#L1300).

시각 자료: [데스크톱 실행](desktop-running.png), [모바일 실행](mobile-running.png), [가로 화면](landscape-running.png), [재생성한 포즈 시트](preview-regenerated.png).

## 8. 재현된 문제와 우선순위

P1은 특정 사용 흐름을 중단시키는 문제, P2는 기능·접근성·유지보수에 직접 영향이 있는 문제, P3는 국소적인 표시·도구 개선이다. 이 등급은 보안 취약점 등급이 아니다.

### P1 — 없는 파일 요청으로 개발 서버 프로세스가 종료됨

위치: [server.mjs:23](../NeonStride/neon-stride/server.mjs#L23).

`res.writeHead(200)`을 먼저 호출한 뒤 `await readFile(file)`을 실행한다. 읽을 파일이 없으면 catch에서 다시 `writeHead(404)`를 호출해 `ERR_HTTP_HEADERS_SENT`가 발생하고 Node 프로세스가 exit code 1로 종료된다. `/missing.txt`와 `/favicon.ico`에서 각각 독립 프로세스로 재현했다. 일반 `/`와 `/engine.js`는 정상이다.

수정 방향은 파일을 먼저 읽고 성공 후 200 응답을 쓰는 것이다. 실패 시에는 404 응답을 한 번만 쓰고 프로세스를 유지해야 한다. 회귀 테스트는 없는 파일 응답 확인 뒤 같은 서버에 정상 파일을 다시 요청하는 방식이 유효하다. 이 문제는 `server.mjs`를 실행할 때 적용되며, `.openai/hosting.json`의 정적 호스팅이 동일한 서버를 쓴다고 단정할 수는 없다.

### P1 — 작은 화면과 가로 화면에서 플레이 영역이 화면 밖으로 내려감

위치: [모바일 최소 높이](../NeonStride/neon-stride/dist/style.css#L844), [터치 버튼 표시](../NeonStride/neon-stride/dist/style.css#L969), [낮은 화면 최소 높이](../NeonStride/neon-stride/dist/style.css#L1027).

320×568에서 게임 영역은 y=180~670이고 터치 버튼은 y=546~611이다. 버튼의 대부분과 게임 화면 하단이 초기 뷰포트 밖에 있다. 844×390에서는 게임 영역이 y=150~590이라 하단 200px가 보이지 않고, 너비가 600px보다 크므로 터치 버튼도 숨겨진다. 768×1024에서도 버튼은 표시되지 않는다. 화면 탭·스와이프 경로는 남아 있지만 모바일 전용 버튼 안내와 실제 표시 조건이 어긋난다.

수정 방향은 실제 남은 화면 높이로 게임 영역을 맞추고, 짧은 화면에서 헤더·설정·안내를 압축하는 것이다. 터치 버튼 노출 여부는 너비에 더해 coarse pointer 여부를 고려해야 한다. `touch-action: none`이 게임 영역에 걸려 있어 영역 내부에서 페이지 스크롤로 문제를 우회하기도 불편하다. [가로 캡처](landscape-running.png)와 [측정 JSON](browser-results.json)에 근거가 있다.

### P2 — 전역 Space 처리와 버튼의 기본 키보드 조작이 충돌함

위치: [app.js:199](../NeonStride/neon-stride/dist/app.js#L199).

난이도 버튼만 Space 예외 처리를 하고, 나머지 버튼에 포커스가 있어도 전역 핸들러가 `preventDefault()`와 게임 조작을 실행한다. 정지 상태에서 도움말 버튼에 포커스를 두고 실제 브라우저 키 입력으로 Space를 보내면 도움말은 열리지 않고 게임이 재개됐다. 같은 버튼을 클릭하면 정상적으로 도움말이 열린다.

수정 방향은 버튼·링크·입력 필드 등 대화형 요소의 기본 키 동작을 우선하도록 입력 범위를 조정하는 것이다. 실제 focus와 브라우저 기본 동작을 쓰는 테스트가 필요하다.

### P2 — UI 테스트 일부가 앞선 테스트의 실행 결과에 의존함

위치: [interface.test.mjs:246](../NeonStride/neon-stride/tests/interface.test.mjs#L246), [323](../NeonStride/neon-stride/tests/interface.test.mjs#L323), [378](../NeonStride/neon-stride/tests/interface.test.mjs#L378).

전체 40개는 통과하지만 다음 명령으로 난이도 테스트만 실행하면 실패한다.

```powershell
node --test --test-name-pattern="difficulty selection" tests/interface.test.mjs
```

실제 오류는 `TypeError: frame is not a function`이다. 앞선 테스트에서 `app.js`를 가져와 이벤트 핸들러와 프레임 함수를 초기화해야 다음 테스트가 동작하기 때문이다. 공유 DOM·게임 상태·시간을 재사용하는 구조도 있다.

수정 방향은 시나리오별 fixture를 만들고 각 테스트가 독립적으로 초기화·실행·정리하도록 구성하는 것이다. 앱 초기화를 함수로 내보내거나 테스트별 독립 호스트를 사용하는 방식이 적절하다. 이는 현재 게임의 난이도 기능이 고장났다는 뜻이 아니라 테스트의 독립성과 실패 추적에 관한 문제다.

### P2 — 동작 줄이기 설정의 적용 범위가 불완전함

위치: [renderer.js:211](../NeonStride/neon-stride/dist/renderer.js#L211), [1300](../NeonStride/neon-stride/dist/renderer.js#L1300), [style.css:1129](../NeonStride/neon-stride/dist/style.css#L1129).

설정을 읽어 대기 화면의 거리 이동은 멈추지만, 하늘의 이동 효과와 캐릭터의 달리기 포즈는 계속 시간에 따라 바뀐다. 브라우저에서 reduced=true인 새 Scene의 대기 화면을 시간 0과 1로 그렸을 때 픽셀이 바뀌는 것을 확인했다. CSS는 흔들림과 결과창 애니메이션은 끄지만 `impact-flash`는 끄지 않는다. 설정 변경을 듣는 이벤트도 없어 열린 페이지에서 OS 설정을 바꾸면 즉시 반영되지 않는다.

플레이에 필요한 이동과 장식 효과를 나누고, 대기 화면의 장식 움직임·충돌 플래시·설정 변경을 함께 처리하는 것이 적절하다.

### P2 또는 조작 정책 결정 — 모바일 슬라이드 버튼은 길게 눌러도 유지되지 않음

위치: [app.js:248](../NeonStride/neon-stride/dist/app.js#L248), [engine.js:138](../NeonStride/neon-stride/dist/engine.js#L138).

키보드는 `slide(true)`를 사용하고 키를 놓을 때 해제하지만, 모바일 버튼은 `slide()`만 호출한다. pointerup 없이 1.1초를 진행하면 슬라이드는 이미 종료되고 `slideHeld=false`다. 따라서 모바일에서 누르는 동안 숙이기를 기대하면 안내와 경험이 다를 수 있다.

탭으로 0.9초 동작하는 것이 의도라면 안내에 명시하면 된다. 길게 누르는 방식을 제공하려면 pointer capture와 pointerup / pointercancel 정리를 포함해야 한다. 현재 두 방식이 같은 조작 정책이라고 설명해서는 안 된다.

### P3 — 어려운 난이도에서 속도 막대가 시작부터 포화됨

위치: [app.js:136](../NeonStride/neon-stride/dist/app.js#L136).

### P3 — 미리보기 시트가 8프레임인데 라벨은 3개만 정의돼 있음

## 9. UI와 접근성

장점은 일관된 어두운 네온 테마, 큰 점수와 시작 버튼, 명확한 난이도 선택, 결과 통계, 한국어 안내, focus-visible 스타일, 버튼의 aria-label, 난이도의 aria-pressed, 네이티브 dialog 사용이다. 375×812 세로 화면에서는 점프·슬라이드 버튼이 모두 뷰포트 안에 있고 가로 넘침은 관찰되지 않았다.

제약도 있다. 장식 문구와 일부 안내가 6~8px로 매우 작다. 실제 게임의 장애물 종류나 도착 시점을 스크린리더가 이해할 텍스트 채널은 없으며, Canvas의 aria-label은 장면 설명 수준이다. 상태 변경·결과창에 대한 live 알림과 포커스 이동도 구현되어 있지 않다. 전체 접근성 기준 준수 여부를 측정한 결과는 아니며, 실제 스크린리더와 대비 측정이 추가로 필요하다.

HUD 상단과 일부 장식 DOM은 Canvas 위에 놓이므로, 화면 전체가 같은 터치 표면이라고 가정해서도 안 된다. 현재 스와이프는 단일 `touchOrigin`만 사용하고 pointerId나 화면 밖 놓기 처리를 하지 않는다. 멀티터치·영역 밖 이동은 확장된 입력 테스트 대상으로 남는다.

## 10. 성능과 리소스

현재 크기와 의존성은 가볍다. 외부 JS 패키지가 없고, 장애물 목록이 제한되어 있으며, DPR을 최대 2로 제한한다. HUD는 약 33ms마다 갱신해 모든 프레임에서 텍스트 DOM을 바꾸지 않는다. 엔진 추가 검증에서도 장애물이 계속 누적되는 현상은 없었다.

브라우저에서 1440×1000, DPR 1, 동일 장면 60프레임의 Canvas 명령 제출 비용을 측정한 마지막 실행은 중앙값 약 1.8ms, p95 약 4.2ms, 최대 약 5.1ms였다. 이는 동기 JS와 Canvas 명령 호출 측정이며 GPU·컴포지터·화면 표시 완료 시간은 포함하지 않는다. 실기기 FPS나 발열을 보장하는 수치로 해석하면 안 된다.

개선 후보는 정지·게임오버 상태에서도 매 프레임 전체 장면을 다시 그리는 점, 매번 만드는 그라데이션, 정적으로 재계산하는 창문·별·스카이라인, shadowBlur 효과다. 먼저 정적 배경 캐시와 정지 상태의 무효화 기반 렌더링을 검토하는 편이 적절하다. 현재 측정만으로 WebGL로 교체해야 한다는 결론은 나오지 않는다.

긴 프레임의 dt 상한이 없어 메인 스레드가 오래 막히면 입력 기회 없이 여러 물리 스텝을 한 번에 따라잡는다. 충돌 누락을 방지하는 장점과 반응 기회가 줄어드는 단점이 공존한다. 끊김이 큰 상황에서 자동 일시 정지할지, 제한된 시간만 진행할지는 게임 정책으로 정하고 시험해야 한다.

## 11. 저장소·네트워크·안전성

게임 진행과 기록은 클라이언트에 있다. 코드에 로그인·서버 API·결제·업로드·분석 SDK는 없다. 최고 기록은 `neon-stride-best:<difficulty>` 키로 저장하고, 쉬움은 과거의 공통 키를 읽어 이전 기록을 이어받는다. localStorage 접근 실패는 try/catch로 처리한다. 소리는 사용자가 켠 뒤 Web Audio oscillator로 합성한다.

공용 랭킹이 없으므로 서버 권위 판정이나 부정행위 방어가 없는 것은 현재 범위의 자연스러운 제약이다. 나중에 랭킹을 추가할 때 현재 점수 값을 그대로 신뢰해서는 안 된다는 의미다. 저장값에 Number.isFinite 검사가 없어 사용자가 저장소를 직접 훼손한 경우 Infinity 같은 값이 표시될 가능성은 있으나, 외부 공격 경로로 확인한 것은 아니다.

정적 서버는 127.0.0.1에만 바인딩하고, 경로를 resolve한 다음 루트 경계와 구분자를 검사한다. Windows 백슬래시를 넣은 탈출 형태는 404였으며 프로세스도 유지됐다. `/../package.json`은 URL 정규화 후 루트 안의 없는 파일 요청이 되어 서버 종료 버그를 일으켰지만, 저장소의 package.json을 읽어낸 것은 아니다.

동적 innerHTML 사용은 고정된 효과음 SVG 문자열로 제한되어 있다. 분석한 코드에서는 사용자 입력을 HTML에 삽입하는 경로를 발견하지 못했다. 이것이 포괄적인 보안 인증을 의미하지는 않는다.

외부 런타임 네트워크 의존성은 Google Fonts CSS import다. 따라서 단일 HTML은 게임 코드·스타일·아이콘을 담지만 폰트까지 완전히 자체 포함하지는 않는다. 네트워크가 없을 때 폴백 글꼴을 쓰도록 되어 있으며, 같은 서체와 배치를 보장하려면 로컬 폰트 또는 시스템 폰트를 선택해야 한다. 이번 검증의 `file://` 성공은 네트워크 차단 상태 검증과는 구별된다.

## 12. 테스트 품질

40개 중 엔진 검증이 26개, 애니메이션 6개, 인터페이스 8개다. 엔진에는 점수·속도, 점프 횟수, 공중 슬라이드, 함정, 재시작, 긴 dt 충돌, 난수 생성, 난이도별 10분 자동 조작, 낙하 통계 동결이 포함된다. 애니메이션에는 관절 길이, 발 접지, 보간 경계의 연속성, 팔 스윙, 보행 주기, 낙하 포즈가 있다.

UI 테스트는 직접 작성한 최소 DOM과 Proxy Canvas로 실제 모듈을 실행한다. 누락된 요소, 유효하지 않은 좌표, 상태 전환 오류를 빠르게 찾을 수 있어 유용하다. 그러나 실제 브라우저의 레이아웃·기본 키보드 동작·포인터 캡처·폰트·그림자·대화상자 포커스 동작을 대체하지는 못한다. 이번에 발견한 모바일 높이와 Space 충돌이 그 경계에 해당한다.

기존 테스트에는 HTTP 서버 요청, standalone 생성, 실제 브라우저 E2E, 시각적 회귀 비교, 여러 난수 시드의 반복이 포함되어 있지 않다. 이번 분석에서 일부 범위를 외부 진단으로 확인했지만, 이 진단이 저장소의 자동 테스트에 통합된 것은 아니다. 특히 UI 테스트의 독립성을 먼저 고친 뒤 필요한 소수의 브라우저 회귀 테스트를 더하는 순서가 합리적이다.

## 13. 빌드·배포·문서화

`npm start`는 dist를 제공하는 개발 서버를 실행하고, 빌드 도구는 engine → renderer → app 순서로 합친 후 import/export를 문자열 치환으로 제거한다. `vm.Script`로 문법을 검사하고 CSS·SVG·JS를 HTML에 삽입한다. 출력에 외부 script src와 기존 CSS 링크가 남았는지도 검사한다.

현재 파일에는 이 단순 빌더가 정상 작동했다. 임시 복사본에서 생성한 HTML과 저장소의 기존 HTML은 둘 다 파일을 직접 열어 시작하고 1초 뒤 10점을 표시했다. 기존 79,960바이트와 재생성 89,162바이트 사이 차이는 JS AST 비교에서는 동일했고 CSS도 공백·소수점 표기를 정규화하면 동일했다. 단순 텍스트·토큰 비교는 포맷 차이로 실패하므로 이를 곧바로 오래된 배포판이라고 해석하면 안 된다.

빌더는 범용 번들러는 아니다. 여러 줄 import, export 재노출, 동적 import, 별도 자산 추가 같은 구조 변경에는 기존 정규식이 대응하지 않을 수 있다. 현재 고장난 것은 아니지만 모듈이 늘 때 주의할 제약이다. `package.json`에 build 명령이 없고 빌드가 테스트와 연결되어 있지 않아 향후 배포판 누락 위험은 있다.

호스팅 설정은 `.openai/hosting.json`에서 정적 디렉터리 `dist`를 지정한다. 이 설정만으로 공개 배포가 현재 정상이라고 결론 내릴 수는 없다. 개발 서버의 `no-store`도 개발 목적에 맞는 설정이며, 정적 호스팅의 실제 캐시 정책으로 일반화하면 안 된다.

README는 제목 한 줄뿐이다. 실행 디렉터리, 요구 Node 버전, 명령어, 소스가 dist에 있다는 사실, standalone 생성법, 조작 방식, 테스트, 미리보기 재생성, 배포 방식을 문서화해야 한다. 추적 파일에는 CI 워크플로·명시적 엔진 버전·라이선스 파일이 없다. 의존성이 없는 현 상태에서 lockfile 부재만을 공급망 문제로 볼 근거는 낮다.

Windows PowerShell에서는 이 환경의 실행 정책 때문에 `npm.ps1`이 차단됐다. 정책을 바꾸지 않고 아래처럼 실행할 수 있다.

```powershell
cd C:\Users\gimin\Desktop\NeonStride\NeonStride\neon-stride
npm.cmd start
node --test
node build-standalone.mjs
```

서버와 테스트·빌드는 목적에 따라 각각 실행한다. 서버 주소는 `http://127.0.0.1:4173`이다. 분석에서는 원본 배포판을 덮어쓰지 않도록 임시 복사본에서 빌드했다.
